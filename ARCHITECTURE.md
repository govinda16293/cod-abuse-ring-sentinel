# Architecture

Stage by stage, with the reasoning for each choice. The leakage audit table is in
[docs/leakage_audit.md](docs/leakage_audit.md) and is generated by the code, not
maintained by hand.

## Overview

```
                        ┌──────────────────────────────────────────┐
  src/config.py ───────►│ every knob + a one-line defence, seeded   │
                        └──────────────────────────────────────────┘
                                          │
   ┌──────────────────────────────────────▼───────────────────────────────────┐
   │ PHASE 1  generate_data.py                                                │
   │   customers · devices · addresses · phones · orders · returns            │
   │   + ground_truth (SEPARATE FILE, never joined as a feature)              │
   │   ring-grouped split · temporal split · test set frozen + SHA-256        │
   └──────────────────────────────────────┬───────────────────────────────────┘
                                          │
   ┌──────────────────────────────────────▼───────────────────────────────────┐
   │ PHASE 2  features.py — point-in-time event replay                        │
   │   orders and returns become timestamped events, replayed in order        │
   │   1 resolve links this order declares (device / address text / MSISDN)   │
   │   2 union into the identity graph using ONLY prior activity              │
   │   3 emit the feature row                                                 │
   │   4 fold this order's own behaviour into state  ← strictly after (3)     │
   └──────────────────────────────────────┬───────────────────────────────────┘
                                          │
   ┌──────────────────────────────────────▼───────────────────────────────────┐
   │ PHASE 2b leakage_audit.py — GATE, runs before any model exists           │
   │   delete every row after a cutoff, recompute, require bit-identical      │
   │   output. Any difference raises LeakageError and stops the pipeline.     │
   └──────────────────────────────────────┬───────────────────────────────────┘
                                          │
   ┌──────────────────────────────────────▼───────────────────────────────────┐
   │ PHASE 3  train.py     LightGBM → isotonic calibration (fit on val only)  │
   │ PHASE 4  threshold.py cost curve in ₹ → 3-band policy (selected on val)  │
   │ PHASE 5  evaluate.py  frozen test set, scored ONCE, thresholds read back │
   │          explain.py   TreeSHAP → evidence sentences → LLM writer         │
   │ PHASE 6  streamlit_app.py  batch · review queue · per-order explanation  │
   └──────────────────────────────────────────────────────────────────────────┘
```

## Phase 1 — synthetic data generator

Seven tables. Ground truth (`ring_id`, `ring_type`, `is_abuse`, `household_id`,
`hn_type`) is written to a **separate file** and is never available to the
feature builder.

**Population.** 122,755 customers, 508,349 orders, 18 months. Order volume ramps
across the window because signups are spread over time — a property that matters
later and is disclosed rather than hidden.

**Rings.** 512 rings, sized lognormally (median ≈ 5, clipped 3–12). Five
signatures that differ in *which identifier they share*, because a detector that
only knows one of them will look excellent on a blended recall number and fall
over on the rest:

| | Shares | Distinct | Campaign shape |
|---|---|---|---|
| R1 shared_device | 1–2 devices | addresses, phones | 14–56 day window |
| R2 address_fuzz | one flat, fuzzed spellings | devices, phones | 14–56 days |
| R3 phone_family | adjacent MSISDN block | devices, addresses | 14–56 days |
| R4 burst_value | **nothing** | everything | 3–10 days, tenure < 14d, 2.1× value |
| R5 hybrid | 2 mechanisms, partially | — | + benign filler orders |

Ring accounts also place a small number of ordinary orders labelled 0, so the
model cannot treat "account belongs to a ring" as equivalent to "this order is
abuse".

**Hard negatives (9.8% of customers).** Each is built to trip one naive rule:

| | Construction | Naive rule it defeats |
|---|---|---|
| H1 joint_family | 3–6 accounts, one flat, shared household device, **60% get fuzzed address variants**, ordinary behaviour, orders spread over months | "same address AND device" |
| H2 hostel_pincode | 15–40 unrelated residents, one building, own devices | "pincode concentration" |
| H3 high_returner | one account, fashion, 45–65% return rate, prepaid-heavy, 500+ day tenure | "return rate > 40%" |
| H4 device_resale | one device, two owners, >90 day gap | "device on 2 accounts" |

The H1 fuzzing detail is load-bearing. In the first build only ring members
produced address variants, which made `addr_variant_count` separate R2 from real
families almost perfectly — a signal that exists nowhere outside a generator.
Fixing that in the *generator* rather than the model is what makes the R2 recall
number worth quoting.

**Splitting.** The split unit is `ring_id` if the order belongs to a ring,
otherwise `household_id`, otherwise `customer_id`. Rings are atomic because
row-level splitting puts ring members on both sides and inflates recall — the
single most likely reason a panel would dismiss this project. Households are
atomic for the mirror-image reason: half a joint family in train lets the model
memorise the address, and the hard negative stops being hard.

**Freezing.** The test set's order ids are written and SHA-256 hashed at
generation time, together with a content hash of the test rows.
`evaluate.py` re-verifies both before it does anything else.

**Temporal split.** Train months 1–12, test 13–18. Rings must not cross: any ring
with campaign orders before the boundary is dropped from the temporal test set
(63 rings, 813 orders). Ordinary customers and households are *not* dropped when
they span the boundary — that is the real production setting, and dropping them
would leave a test set made only of accounts whose first ever order falls after
the boundary.

## Phase 2 — point-in-time features

63 features computed, 49 used (see the feature-set experiment below).

The replay is the whole design. State is a set of dictionaries and a union-find
over customers with mergeable, time-decayed aggregates. For each order event:

1. **Resolve declared links.** The device id, the typed address string and the
   MSISDN are all present in the checkout event, so linking on them is legitimate
   at placement time.
2. **Union into the graph** against customers who have transacted *before now*.
   Components only ever grow, which is exactly the as-of semantics required.
3. **Emit** the row from current state.
4. **Fold** this order's behaviour into state — after emission.

Returns are separate events that fire at `return_ts`. A return that has been
requested but not yet settled is invisible to every feature. `cust_return_rate`
at time *T* counts only returns settled before *T*.

**Address clustering** uses a deterministic canonical key: `(pincode, flat token,
canonical token set)` after abbreviation expansion. The obvious alternative —
greedy fuzzy matching inside a `(pincode, flat)` block — is order-dependent, so
an address first seen in month 15 can become the representative that bridges two
month-3 variants, silently moving a month-3 feature row. That fails the causality
gate. A production fuzzy matcher would have to be rebuilt over a trailing window
to stay causal.

**Phone adjacency** is derived numerically from the MSISDN (±5), never from the
generator's `phone_family_id`. The relation is static; what is time-dependent is
which neighbours have transacted yet, which the replay handles.

**Component statistics** survive union: size, orders, returns, COD count, value,
summed and minimum signup, plus exponentially decayed order and growth counters
(τ = 7d and 30d) that are decayed to a common reference time before merging.

### Why 49 features and not 63

Roughly a third of the as-of features are running totals that inflate as the
dataset ages. Eight scale-free replacements were added (orders per day per
customer / device / address / cluster member; pincode and component volume as a
*share* of marketplace volume so far).

Choosing between feature sets could not be done on the temporal model's own
validation fold, because that fold sits inside months 1–12 and contains none of
the drift. The selection protocol therefore uses only data up to month 12:

```
fit  months 1-8   →   calibrate month 9   →   select on months 10-12
                                              (rings non-crossing throughout)
```

| Variant | Features | Cost/1000 on the selection fold |
|---|---|---|
| A pre-improvement | 55 | ₹15,262 |
| B + rate features | 63 | ₹18,689 |
| **C stable only** | **49** | **₹14,309** |

C ships. The 1–3 month gap in the selection fold turned out to be too small to
contain the shift that appears at month 13 — an earlier pre-bugfix run of this
comparison on the test set showed C failing to beat A there. That is itself a
finding about how to validate for drift: a selection fold must span the horizon
you intend to deploy over.

## Phase 2b — the causality gate

`assert_prefix_invariance(cutoff="2026-01-01")` truncates orders, returns *and*
the reference tables to entities existing by the cutoff, recomputes every
feature, and requires `np.array_equal` against the full run. If any feature had
touched a later row, deleting those rows would move it.

Result: **all 63 features bit-identical across 272,959 pre-cutoff orders.**

This is a gate, not a report. It runs before `train.py` in `run_all.py`, and it
raises `LeakageError` naming the offending columns and row counts.

A second, cheaper defence sits in `build_features` itself: it refuses to run if
handed any column outside an explicit allow-list, so `return_flag`,
`delivered_flag`, `building_id`, `phone_family_id` and the generator's latent
behaviour parameters cannot reach feature code by accident.

## Phase 3 — the scorer

**LightGBM, not a GNN.** The graph structure that matters is already summarised
into ~15 as-of component features. A boosted tree over those is defensible
feature by feature under questioning, trains in 18 seconds, and gives exact
per-prediction attribution via TreeSHAP. A GNN would add message passing over an
identity graph that is mostly stars and small cliques, and would make the
causality guarantee substantially harder to prove, because neighbourhood
aggregation has to be time-masked at every hop. If the graph had dense
multi-hop structure worth propagating over, that trade would look different.

**Isotonic, not Platt.** The validation fold has ~50k rows and ~1.5k positives —
enough for a non-parametric monotone fit — and raw boosted-tree scores are not
sigmoid-shaped near zero, which is where every threshold here lives. Result:
Brier 0.0070, ECE 0.0018.

**Calibrator fit on validation only** (`cv="prefit"`). Fitting it on training data
calibrates against scores the model has already memorised.

**No class reweighting.** Reweighting distorts the output scale, and Phase 4
depends on thresholding a probability that means what it says.

## Phase 4 — the cost policy

Every constant is in `CostConfig`, now tagged `[SOURCED]`, `[DERIVED]` or
`[ASSUMED]`, with the published figure behind it. Full derivation against
Delhivery / Shiprocket rate cards and category margin benchmarks:
[docs/cost_model.md](docs/cost_model.md). Four of eleven constants are sourced,
two derived from published labour rates, and five are assumptions with no public
figure. Reverse shipping (₹85, i.e. 113% of forward against a cited 80–100% RTO
band) and `gross_margin_rate` (a contribution margin, not a gross one) are both
flagged as imperfect and deliberately left unchanged — altering them would change
band selection and require re-scoring the frozen test set.

The defence of the result is therefore [docs/cost_sensitivity.md](docs/cost_sensitivity.md):
28 cost worlds, every economic constant at ±50%, reviewer accuracy 70–95% and
review capacity 2–10%, each re-running selection from scratch on validation. The
three-band policy beats both baselines in all 28, and the band structure never
collapses. The only real breaking point is a review capacity below 2.13%, where
the shipped policy becomes infeasible rather than merely suboptimal.

Costs are per order and scale with order value, so the optimum is swept rather
than derived.

Three bands, selected jointly on validation under a hard constraint that no more
than 5% of volume may go to humans:

```
p <  0.0343              pass          94.92% of volume
0.0343 <= p < 0.3441     human review   2.32%
p >= 0.3441              force prepay   2.76%
```

A reviewer is modelled as correct 88% of the time and costing ₹32; when wrong,
the full FN or FP cost lands anyway on top of the review fee. Two baselines are
computed for context: doing nothing, and switching COD off entirely.

The band search bounds were initially too narrow and the optimum pinned to the
lower edge at exactly 0.05 — a signal that the answer was the bound, not the
optimum. Widened to 0.004, after which the solution is interior.

## Phase 5 — explanation and evaluation

**The boundary: the classifier decides, the LLM writes.** The language model
never sees the label, never sees the threshold, and its output has no path back
into the decision. It receives a frozen structured payload — order facts, the top
TreeSHAP contributions already rendered as evidence sentences, counter-evidence,
and rule-generated caveats — and turns it into prose.

That ordering also makes the explanation auditable against the attributions.
Asking a model "is this fraud?" would produce a second, uncalibrated classifier
wearing a justification costume.

Attribution is taken on the booster's margin, not the calibrated probability:
isotonic regression is a monotone post-hoc map, so it changes the number but not
the ordering or the reasons.

Without `ANTHROPIC_API_KEY` a deterministic template writer produces the same
content, so the repo runs offline.

**Caveats are generated, not boilerplate.** Rules over the same feature row
produce statements like "at least one account in this cluster is over a year old;
order data alone cannot separate a co-ordinated group from a genuine shared
household."

**Evaluation** verifies the test-set hash, reads thresholds back from
`artifacts/policy.json`, scores once, and writes metrics, per-ring-type recall,
false positives by legitimate population, PR curve, reliability diagram and cost
curve. Nothing in `evaluate.py` selects a threshold or re-fits anything.

## What I would change with real data

1. **Replace the address canonicaliser with a geocoder.** Text normalisation is
   the weakest link in the R2 path and its recall is capped by a synonym list.
   Real production systems resolve to a lat/long or a delivery-point id. The
   causal constraint stands: the geocode index must be snapshotted, not
   back-filled.

2. **Recalibrate on a trailing window and monitor per segment.** The temporal
   result says the score distribution shifts hard. In production I would refit
   the isotonic layer weekly on recent settled outcomes, alarm on the flag rate
   for the new-account segment specifically, and treat a moving q99 of legit
   scores as a paging signal.

3. **Model the reviewer as a feedback loop.** Here the reviewer is a fixed 88%
   accuracy constant. In reality review outcomes are the label source, which
   creates selection bias: orders that are auto-blocked never generate a return
   outcome, so the training set stops containing the cases the model is most
   confident about. That needs a deliberate exploration hold-out.

4. **Give R4-style rings something to link on.** No feature engineering fixes an
   information limit. What would: session and fingerprint telemetry, delivery
   OTP/geolocation at the door, or cross-merchant identity signals — things a
   payments processor can see and a single merchant's order log cannot.

5. **Cost constants become a negotiation, not a config file.** `product_loss_
   fraction`, `churn_prob_given_blocked` and `customer_residual_value_inr` are
   the three numbers that move the threshold most; they should come from the
   merchant's own finance team, and the cost curve should be re-swept per
   merchant rather than shipped as a global default.
